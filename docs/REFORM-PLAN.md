# WAF 개편 계획과 검토 범위

## 유지하는 형태

기존 Next.js 관리 화면의 탐색, 카드, 차트, 규칙 편집 화면과 Nginx/ModSecurity → Fluent Bit → Kafka → 저장소 구조를 유지한다. 서비스와 Kafka 토픽을 새 이름으로 이관하지 않는다. `waf-realtime-events`는 감사 이벤트 입력이다.

계획 담당과 구현 담당을 분리한다. 구현 결과는 별도 검토 후 통합한다. 기존 작업 폴더의 미커밋 수정과 실험 파일은 그대로 유지한다. 기존 미추적 ClickHouse 소비자와 관련 배포 설정만 검토·정리한 사본으로 포함한다. 로컬 SQL 프록시, 실험 HTML, 실제 환경 파일은 포함하지 않는다.

## 공통 계약

### 인증

- Google 로그인 시작과 state 검증은 social API가 담당한다.
- 브라우저 콜백은 `/login/oauth2/code/google`의 Next 서버 라우트다.
- 세션 토큰 `WAF_AT`는 `HttpOnly`, `SameSite=Lax`, `Path=/` 쿠키로 관리한다. HTTPS에서는 `Secure`를 사용한다.
- dashboard API는 같은 JWT 계약을 검증하며 SSE에도 인증을 적용한다.
- 쿠키 기반 변경 요청은 출처를 확인한다. 브라우저 코드에서 토큰을 읽거나 backend 주소로 직접 변경 요청을 보내지 않는다.
- 로그아웃은 브라우저 세션 쿠키를 지운다. 이미 복사된 JWT의 즉시 폐기는 구현 범위 밖이며 토큰 만료까지 유효할 수 있다.

### 규칙과 화이트리스트

- `/api/rules`의 공통 모델은 `name`, `description`, `enabled`, `severity`, `category`, `variables`, `operator`, `operatorData`, `actions`, `priority`와 숫자 `id`다.
- `/api/whitelist`는 IPv4/CIDR 초안을 관리한다. IPv6는 아직 지원하지 않는다.
- 저장은 JSON 파일을 원자적으로 교체하며, 저장 실패 후에는 성공한 것처럼 메모리 상태를 변경하지 않는다.
- 이 저장소는 단일 프로세스용이다. 공유 파일에 여러 dashboard 인스턴스를 동시에 쓰게 하지 않는다.
- CRUD와 `enabled` 변경은 **초안 저장**이다. 실제 ModSecurity 설정 변경이나 적용 확인을 뜻하지 않는다.
- 실제 Nginx 구문 검증·reload·적용 확인이 연결되기 전까지 `/api/rules/deploy`는 `501`을 반환한다. 성공한 배포 이력을 생성하지 않는다.

### 조회와 이벤트

- 저장소가 비어 있으면 빈 결과, 조회가 실패하면 오류를 반환한다. 임의 경고, 가짜 정상 상태, 가짜 배포 성공을 만들지 않는다.
- 높은 심각도와 실제 차단 여부를 구분한다. HTTP 403 기반 추정은 ModSecurity 적용 증명이 아니다.
- Kafka 소비자는 필수 저장 작업 성공 후에만 오프셋을 커밋한다. 실패한 이벤트를 건너뛰고 다음 이벤트의 오프셋을 커밋하지 않는다.
- 재처리로 중복이 생길 수 있다. exactly-once 전달이나 무손실을 보장한다고 문서화하지 않는다.
- ClickHouse 변경은 기존 테이블을 삭제하지 않는 추가 컬럼 마이그레이션으로 제공한다.
- 최근 경고는 저장소에서 조회한다. 실시간 경고 생산자가 연결되지 않은 `/api/alerts/stream`은 `501`로 표시하며, 실시간 로그 SSE와 구분한다.
- InfluxDB의 이벤트 식별 태그는 같은 시각 이벤트의 덮어쓰기를 방지하지만 시리즈 수를 증가시킨다. 운영 처리량과 보관 기간에 따른 메모리·인덱스 비용 검증이 필요하다.

## 검증

회귀 테스트는 인증 거절·만료·state 불일치, 저장 실패·재시작, 조회 장애, SSE 재연결, 저장 실패 시 커밋 금지, 실패 배치 보존을 다룬다. 프런트엔드는 타입과 린트 오류를 빌드에서 무시하지 않는다.

CI와 로컬 검증은 외부 운영 자격 증명 없이 실행한다. 실제 Google 계정 로그인, 실행 중인 Nginx의 규칙 적용, Kafka/저장소 전체 연결, Kubernetes 배포는 별도의 통합 환경에서 검증해야 한다. 모의 응답으로 확인한 UI와 실제 전체 시스템 검증을 구분해 보고한다.
